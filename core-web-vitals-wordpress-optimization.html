How I improved Core Web Vitals
from 45 to 92 on a WordPress site

A score of 45 on mobile PageSpeed is more common than people think — and it almost always comes from the same handful of causes. This is a real walkthrough of an audit I ran on a WordPress site for a US real estate client. I'll show you exactly what I found, what I fixed, and in what order.

No generic tips. No "install WP Rocket and call it a day." This is the actual process.

Step 1 — Run the real audit first

Before touching anything, I always start with three tools in this order:

  1. Google PageSpeed Insights — for the CWV scores and field data (real user data from CrUX)
  2. WebPageTest — for the waterfall chart and third-party breakdown
  3. Chrome DevTools Performance tab — to trace exactly what's blocking the main thread

The mistake most people make is going straight to PageSpeed and treating the "Opportunities" list as a to-do list. That list is generic. The waterfall is where the real story is.

Key insight

Field data (from CrUX) is what actually affects your rankings. Lab data is just a diagnostic tool. Always look at field data first — if you don't have enough traffic to populate it, focus on lab data with a throttled mobile connection.

Three separate problems causing three separate failures. Let me break down exactly what caused each one.

Problem 1 — LCP: the hero image was loading too late

LCP at 7.2s on mobile is bad. The largest element on the page — the hero image — was being loaded by a lazy-loaded slider plugin. The browser was:

  • Waiting for JavaScript to parse and execute
  • Then rendering the slider plugin
  • Then discovering the image
  • Then downloading it at full resolution (2400px wide, 380KB)

The fix had three parts.

Fix 1a — Preload the LCP image

Add this to <head> — it tells the browser to start downloading the image immediately, before it even parses the body:

<!-- Add to wp_head via functions.php --> <link rel="preload" as="image" href="/wp-content/uploads/hero.webp" fetchpriority="high">

Fix 1b — Replace the slider with a static hero

The slider plugin was adding 47KB of JavaScript and 12KB of CSS that blocked rendering. For a hero image that almost nobody interacted with, this was an expensive trade. I replaced it with a static <img> tag with fetchpriority="high" and loading="eager".

Fix 1c — Convert and resize the image

The original PNG was 2400×1200px at 380KB. Mobile users don't need that. I:

  • Converted to WebP (saved 62%)
  • Created responsive sizes with srcset: 480w, 768w, 1200w
  • Added explicit width and height attributes (this also helps CLS)

LCP dropped from 7.2s to 2.1s with just these three changes.

Problem 2 — TTFB: the server was slow before it sent a single byte

A TTFB of 1,840ms means the server was taking almost 2 seconds before sending the first byte of HTML. This is usually a PHP/database problem, not a frontend problem.

On this site it was caused by a combination of:

  • No page caching — every request was running PHP and hitting the database
  • 12 active plugins making database queries on every page load — including 3 that were only used in the admin dashboard but still loaded on frontend
  • Shared hosting without object caching

Fix 2a — Install and configure page caching

I installed WP Rocket and configured it with these specific settings that most people miss:

// WP Rocket config that actually matters Cache lifespan: 10 hours Separate cache for mobile: YES (critical if you have a mobile theme) Cache preloading: ON + sitemap-based Remove query strings: ON DNS prefetch: Add Google Fonts, GTM, analytics domains

Fix 2b — Disable plugins on frontend when not needed

Used the Asset CleanUp plugin to disable 3 heavy plugins (a backup plugin, an admin-only SEO plugin, and a WooCommerce remnant) from loading on frontend pages. This alone removed 180KB of JavaScript from every page load.

TTFB went from 1,840ms to 320ms.

Problem 3 — CLS: things were jumping around on load

CLS of 0.38 is very high — anything above 0.1 is considered poor. The layout shifts were coming from two sources:

  • Images without width/height attributes — the browser doesn't know how much space to reserve, so it reserves none, then the image loads and pushes everything down
  • A cookie consent bar that appeared 800ms after page load and pushed all the content down
  • Google Fonts loading asynchronously and causing a font swap mid-render

Fix 3a — Add explicit dimensions to all images

<!-- Before (causes CLS) --> <img src="photo.jpg" alt="..."> <!-- After (no CLS) --> <img src="photo.jpg" alt="..." width="800" height="533">

Fix 3b — Reserve space for the cookie bar

The cookie consent plugin had an option to show as a fixed bottom bar instead of pushing content. Switched to that. CLS from the cookie bar went to zero.

Fix 3c — Preload and swap fonts properly

<!-- Add font-display: swap to prevent invisible text --> <link href="https://fonts.googleapis.com/css2?family=...&display=swap" rel="preload" as="style" onload="this.rel='stylesheet'">

CLS went from 0.38 to 0.02 — well within the "good" threshold.

The order matters

One thing I want to emphasize: the order in which you fix these things matters. I always fix TTFB first (server-side caching), then LCP (image loading), then CLS (layout stability). If you fix LCP before fixing TTFB, the caching layer might interfere with your preload headers.

Final results

PageSpeed mobile: 45 → 92. LCP: 7.2s → 2.1s. TTFB: 1,840ms → 320ms. CLS: 0.38 → 0.02. Total time to implement: about 6 hours of focused work spread across two days (audit, changes, testing, verifying with real devices).

If you're working on a WordPress site and your CWV scores are poor, start with the waterfall chart, not the opportunities list. The waterfall will show you exactly what's slow and in what order — that's where the real audit begins.
